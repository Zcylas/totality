================================================================================
0. GLOBAL CONVENTIONS (apply across every API in this document)
================================================================================
  - All definition IDs are namespaced Identifiers (e.g.
    totality:salmon, totality:fine_flour).
  - Datapack/data-driven definitions use CODECS and contain NO raw
    runtime Java objects (no Item, Block, EntityType<?>, or bare
    interface references inside a record meant to be data-driven —
    see Section 7b and Section 10b's fixes for the concrete pattern).
    Runtime STRATEGY REGISTRIES resolve identifiers like
    totality:preserve_worst, totality:spawn_entity,
    totality:player_has_quest, totality:manual_processing_check to
    actual behavior.
  - All gameplay mutation is SERVER-AUTHORITATIVE.
  - Definitions are IMMUTABLE. Player progress is MUTABLE component
    state. Never conflate the two.
  - All collections inside immutable records are DEFENSIVELY COPIED.
  - Services performing multi-step operations (starting a cooking
    batch, resolving a harvest, landing a fish) do TRANSACTIONAL input
    consumption and output creation — partial application on failure
    is a bug.
  - Events declare explicitly whether they fire BEFORE or AFTER the
    mutation they describe.
  - Every persistent component has a DATA VERSION and a MIGRATION
    PATH for when its shape changes later.
  - Client sync sends ONLY information the player is permitted to
    know (e.g. another player's private quest state, or an
    undiscovered Codex entry's full data, should never reach a client
    that shouldn't see it).
  - Automated actions (hoppers, automated nets, machine harvesters,
    etc.) explicitly specify whether they award XP, Codex discoveries,
    and records — the default, per the automation-vs-manual philosophy
    established across Fishing/Farming/Cooking, is that they generally
    do NOT, unless a specific system says otherwise.
  - Numeric constants throughout this document are DEFAULTS/
    PLACEHOLDERS for playtesting, not locked balance guarantees, unless
    explicitly marked CONFIRMED/LOCKED.

0a. Acceptance tests (sanity checks worth writing early, not after
    the fact)
--------------------------------------------------------------------------------
  - Perfect cooking cannot remove untreated magical toxins.
  - A Prime garnish cannot excessively elevate Poor primary
    ingredients (elevation cap holds).
  - Merging food stacks cannot make older food read as fresher.
  - Boiling removes valid biological contaminants but does NOT remove
    salt.
  - Repeatedly scanning one already-discovered Salmon cannot
    repeatedly award discovery XP.
  - Disconnecting during a hooked catch cannot reroll the catch.
  - Copying or moving a Cooking batch item cannot duplicate its
    captured ingredients.
  - Another player's Bread cannot complete YOUR First Loaf quest.
  - Breaking a station cannot reset or duplicate its active batch.
  - Stabilized field crops remain performant at large farm scale
    (thousands of blocks).

================================================================================
1. CORE ARCHITECTURAL PHILOSOPHY
================================================================================
  COOKING NEVER ASKS WHERE AN INGREDIENT CAME FROM. It only reads the
  ingredient's culinary properties through a shared interface.

  Gameplay systems (Farming, Fishing, Cooking, Processing, Husbandry,
  Carcass Processing) each own their OWN activity and XP. They do NOT
  own shared concepts like "how fresh is this," "what are the
  conditions here," or "has the player seen this before" — those live
  in shared foundation APIs every gameplay system reads from and
  writes standardized events to.

  Ingredient Potential (from Farming/Fishing/Husbandry/Carcass
  Processing, via the unified Product Condition API) + Cooking
  Execution (the player's rolls) = Finished Dish quality.

  IMPORTANT CORRECTION (this revision): "Butchering will become part
  of Cooking" — a statement that appeared in the original design
  session — is REMOVED and INCORRECT. Carcass Processing is its own
  system (Section 16) with its own ownership boundary, exactly
  parallel to how Processing (Section 7) owns Wheat->Flour and
  Fish->Fillets. Cooking never performs butchering/carcass work
  itself; it only ever reads the resulting ProductConditionComponent
  the same way it reads any other ingredient. Do not build Butchering
  logic inside the Cooking API.

4b. FIX: subject-to-entry mapping layer (was previously assumed,
    now explicit)
--------------------------------------------------------------------------------
  PROBLEM: an identifier like totality:salmon could refer to an entity
  type, a fish species definition, an item, OR a Codex entry — these
  must not be silently assumed to be the same namespace.

  public record CodexSubjectMapping(
          Identifier subjectId,        -- the raw game-object id
          Identifier subjectKind,      -- e.g. totality:entity_type,
                                           totality:item,
                                           totality:fish_species,
                                           totality:crop
          Identifier codexEntryId      -- the actual Codex entry this
                                           resolves to
  ) {}

  A registry of these mappings is what DiscoveryEvent -> Codex entry
  resolution actually uses. Never assume subjectId == codexEntryId.

--------------------------------------------------------------------------------
4c. FIX: typed discovery payloads (replaces the previous undefined
    generic DiscoveryContext)
--------------------------------------------------------------------------------
  PROBLEM: a single untyped/undefined context object would eventually
  force unsafe casts or degrade into one giant unstructured map, since
  the Codex needs to update very different things depending on event
  type (largest fish weight vs. discovered biomes vs. recipe
  relationships vs. cultivar records).

  FIX — use TYPED discovery facts, a small closed set of value shapes
  emitted alongside every event, rather than one grab-bag context:

  public record DiscoveryFact(
          Identifier factType,     -- e.g. totality:weight_kg,
                                        totality:biome_observed,
                                        totality:trait_expressed,
                                        totality:recipe_used
          DiscoveryValue value      -- a small sealed type: NumberValue,
                                        IdentifierValue, TextValue,
                                        BooleanValue — NOT a raw Object
  ) {}

  FIX (this pass): DiscoveryEvent previously carried only a bare
  `subjectId`, which left the exact ambiguity Section 4b's
  CodexSubjectMapping was supposed to solve unresolved — an item, an
  entity type, a crop definition, and a fish-species definition could
  all share the same raw identifier. DiscoveryEvent now carries a full
  CodexSubjectRef (kind + id), not just an id:

  public record CodexSubjectRef(Identifier kind, Identifier id) {}
       -- kind mirrors CodexSubjectMapping.subjectKind (4b), e.g.
          totality:entity_type, totality:item, totality:fish_species,
          totality:crop

  public record DiscoveryEvent(
          UUID playerId, CodexSubjectRef subject, Identifier eventType,
          int amount, List<DiscoveryFact> facts
  ) {}

  Example — Fishing emits on a Salmon catch:
    subject = CodexSubjectRef(totality:fish_species, totality:salmon)
    eventType = totality:caught
    facts = [
      (totality:weight_kg, NumberValue(4.28)),
      (totality:length_cm, NumberValue(54.7)),
      (totality:biome_observed, IdentifierValue(minecraft:river)),
      (totality:condition, IdentifierValue(totality:pristine))
    ]

  The Codex listener reads only the fact TYPES it understands and
  ignores the rest — this keeps Fishing (or any emitter) free to add
  new facts later without the Codex needing prior knowledge of every
  possible emitter's internals, while staying fully typed (no unsafe
  casts).

4e. Spyglass scanning — FULLY SPECIFIED (was previously just named,
    not defined — this was flagged as a real gap)
--------------------------------------------------------------------------------
Reference mod confirmed by Stefan: "Field Guide" (Modrinth/CurseForge)
— scan at a distance, unlock a personal log entry per successful scan.
Concrete interaction contract for Totality's version:

  SCANNABLE TARGET TYPES: entities, blocks, crops, fluids, structures
  (extensible set, defined per CodexEntryDefinition via its
  visibilityRuleId / a companion scan-eligibility flag).

  VALIDATION (server-authoritative):
    - Raycast from the player's eye position along their look vector.
    - Line-of-sight required (no scanning through solid blocks).
    - Maximum range: placeholder 24 blocks (tune later).
    - REQUIRED CONTINUOUS OBSERVATION DURATION: placeholder 1.5
      seconds of holding the target in view through the Spyglass
      before a scan registers (prevents "flick past it" scanning,
      matches how Field Guide-style mods create a small deliberate
      moment rather than instant discovery).
    - MOVEMENT: significant camera movement off-target during the
      observation window RESETS the progress timer (does not need to
      be perfectly zero-tolerance, but drifting off the subject
      restarts the hold).
    - COOLDOWN: a short cooldown after a successful scan (placeholder
      1 second) before another scan attempt can begin, to avoid
      spamming.
    - RESCANNING (FIX — this was previously self-contradictory: one
      bullet said rescanning an Observed-or-higher subject "does
      nothing by default," while another said a Studied subject "can
      still be scanned to contribute toward record-tracking facts" —
      those two statements conflicted. RESOLVED, single rule):
      rescanning an already-discovered subject NEVER awards repeat
      discovery XP and NEVER re-triggers a DiscoveryLevel change or
      its associated milestone reward (ties into the acceptance test
      in Section 0a) — but it CAN still update ongoing SPECIMEN
      RECORDS (e.g. "largest observed," per-fact tracking via the
      DiscoveryFact system, Section 4c) if the new scan's data
      qualifies as a new record. Seeing a bigger Salmon updates
      "largest observed Salmon"; it never grants a second "first
      discovery" reward. Facts and discovery-level progress are
      independent tracks (Section 4d) — this rule is just the
      concrete application of that independence to the rescanning
      case specifically.
    - HOSTILE MOBS: an aggroed hostile mob attacking the player
      SHOULD interrupt an in-progress scan (reset the hold timer) —
      keeps scanning from being a completely safe action to spam near
      danger.
    - PARTIAL CLUES: a subject at RUMORED level (heard about, not yet
      observed) can be advanced toward OBSERVED via a successful scan.
    - PHONE NOTIFICATION: fires on any DiscoveryLevel change AND on
      any new specimen record being set (both use the same phone-
      notification hook, Section 4d) — a level-up and a "new largest
      Salmon" are both worth notifying, even though only the former
      counts as a discovery-XP event.
    - MAGICAL/INVISIBLE SUBJECTS: placeholder rule — some Codex
      entries may require an UPGRADED Spyglass (future item tier) to
      even register as scannable, e.g. subjects tagged
      totality:requires_arcane_lens. Base Spyglass works for ordinary
      subjects. Exact upgrade item/tier TBD, not blocking V1.

4e-2. NEW: data-driven Codex progression-rule layer (was missing — the
      Codex needed SOME mapping from "an event/fact happened" to "what
      changes in the player's Codex data," and without an explicit
      layer for this, a Codex listener implementation would end up
      hardcoding rules like "caught means STUDIED" or "processed
      unlocks the processing-outputs section" directly in code)
--------------------------------------------------------------------------------
  FIX (this pass): the previous shape forced EVERY rule to specify a
  `resultingLevel`, but many rules only touch a record/counter/trait/
  section/relationship without changing discovery level at all (e.g.
  "new largest specimen" shouldn't force a level value). Replaced the
  fixed field list with a generic list of PROGRESSION ACTIONS:

  public record CodexProgressionRule(
          Identifier id, Identifier appliesToCategory,
          Identifier triggerEventType,
          Optional<Identifier> requiredFactType,
          List<CodexProgressionAction> actions
  ) {}

  public sealed interface CodexProgressionAction {
      record RaiseLevelTo(DiscoveryLevel level) implements
          CodexProgressionAction;    -- MONOTONIC: only applies if
                                         `level` is HIGHER than the
                                         entry's current level; never
                                         lowers it
      record UnlockSection(Identifier sectionId) implements
          CodexProgressionAction;
      record IncrementCounter(Identifier counterId, int amount)
          implements CodexProgressionAction;
      record UpdateRecordIfBetter(Identifier recordId,
          Identifier sourceFactType) implements CodexProgressionAction;
      record AddDiscoveredTrait(Identifier traitId) implements
          CodexProgressionAction;
      record AddRelation(CodexRelation relation) implements
          CodexProgressionAction;

      -- FIX (this pass): the six actions above all take FIXED values
      -- authored directly into the rule (e.g. AddDiscoveredTrait
      -- always adds the SAME traitId every time it fires). That can't
      -- handle an event that carries an ARBITRARY trait/relation/
      -- amount without authoring one separate rule per possible
      -- value — e.g. a generic "Cooking discovered a new trait"
      -- event shouldn't need a bespoke rule per trait that could ever
      -- be discovered. Added dynamic, FACT-DRIVEN variants:
      record AddTraitFromFact(Identifier sourceFactType) implements
          CodexProgressionAction;    -- reads the actual trait
                                         identifier out of the
                                         triggering event's matching
                                         DiscoveryFact (Section 4c)
                                         instead of a fixed traitId
      record AddRelationFromFact(Identifier sourceFactType) implements
          CodexProgressionAction;    -- same idea, for relations
      record IncrementCounterByEventAmount(Identifier counterId)
          implements CodexProgressionAction;  -- reads
                                                   DiscoveryEvent.amount
                                                   directly instead of
                                                   a fixed authored
                                                   amount
  }

  A rule now declares WHATEVER combination of actions actually
  applies — a rescanning rule (Section 4e) might declare only
  `UpdateRecordIfBetter`, while a first-catch rule declares
  `RaiseLevelTo(STUDIED)` + `UnlockSection(...)` + `IncrementCounter(
  ...)` together. `RaiseLevelTo` is explicitly MONOTONIC — applying it
  when the entry is already at or above that level is a no-op, so
  rules can be layered/re-triggered safely without ever demoting an
  entry.

  A registry of these rules is what the Codex's generic listener
  actually consults — e.g. a rule declares "for fish_species subjects,
  a totality:caught event raises level to STUDIED and unlocks the
  size/bait/habitat sections," rather than that logic living inside a
  bespoke FishingCodexListener class. New categories (Cultivation
  species, Cooking recipes, Materials, etc.) register their OWN
  progression rules against this same generic layer instead of the
  Codex needing built-in knowledge of every possible domain.

4e-3. NEW: aggregate MASTERED milestone conditions (was missing — the
      progression-rule layer above reacts to INDIVIDUAL events, but
      MASTERED (Section 4b's top discovery level) is inherently an
      AGGREGATE condition — "caught 10 times," "all sections
      unlocked," "observed in 3+ habitats" — that can't be expressed
      as a reaction to any single event)
--------------------------------------------------------------------------------
  public record CodexMilestoneCondition(
          Identifier id, Identifier appliesToCategory,
          List<MilestoneRequirement> requirements   -- ALL required,
                                                         unless a
                                                         future
                                                         "any of"
                                                         variant is
                                                         added
  ) {}

  public sealed interface MilestoneRequirement {
      record CounterAtLeast(Identifier counterId, int threshold)
          implements MilestoneRequirement;
      record AllSectionsUnlocked() implements MilestoneRequirement;
      record HabitatCountAtLeast(int count) implements
          MilestoneRequirement;   -- "several habitats observed"
      record AllTraitsDiscovered() implements MilestoneRequirement;
      record RecordAtLeast(Identifier recordId, double threshold)
          implements MilestoneRequirement;
      record RelatedActionsCompleted(Set<Identifier> actionIds)
          implements MilestoneRequirement;
  }

  After EVERY progression-rule application (4e-2), the Codex checks
  whether the affected entry now satisfies any registered
  CodexMilestoneCondition for its category — if so, that entry's
  level is raised to MASTERED via the same monotonic `RaiseLevelTo`
  mechanism (so this doesn't need a separate non-monotonic code path,
  it just becomes another source that can trigger the existing
  action). This keeps individual-event reactions (4e-2) and aggregate
  milestone evaluation (this section) as two distinct, composable
  layers rather than trying to cram aggregate logic into the per-event
  rule shape.

5b. FIX: EnvironmentService with caching (was missing — every system

6d. FIX: Freshness stacking — explicit strategy AND an explicit shared
    enforcement hook (was a real implementation gap on two levels:
    first, storing precise accumulated age units directly on the
    component while claiming "the visible/stacking state stays
    bucketed" doesn't solve anything by itself; second, even with a
    custom equality/merge RULE defined, Minecraft has MANY separate
    code paths that can merge/compare stacks — inventory, shift-click,
    hoppers, ground-item merging, machine inventories, recipe
    remainders — and without ONE shared hook enforcing the custom
    policy, some paths would honor it and others would silently fall

--------------------------------------------------------------------------------
  public enum FreshnessStage { FRESH, AGED, STALE, SPOILED }

  public record FreshnessData(
          FreshnessStage stage,             -- PARTICIPATES in stack
                                                equality/display
          long freshnessAgeUnits,           -- EXCLUDED from default
                                                stack equality —
                                                precise internal
                                                tracking only
          long lastFreshnessUpdateTick,
          float currentPreservationMultiplier
  ) {}

  RULE (unchanged): two stacks are MERGE-COMPATIBLE if their `stage`
  matches, regardless of any difference in the three precise-tracking
  fields. On merge, the result inherits whichever input is FURTHER
  ALONG its decay curve — always the OLDER/WORSE state, never an
  average, never fresher than its worst input (satisfies the "merging
  food cannot make older food fresher" acceptance test, Section 0a).

  FIX: SHARED ENFORCEMENT MECHANISM (new — this is what actually makes
  the rule above implementable everywhere rather than just in one code
  path): register this as ONE central policy through a shared
  registry+service pair that every stack-comparison/merge path in the
  game is routed through, rather than reimplementing custom equality
  checks in each subsystem separately.

  FIX (this pass): SPLIT into a REGISTRY (where component-specific
  policies get REGISTERED) and a SERVICE (which actually PERFORMS
  comparisons/merges) — the earlier single-interface shape looked like
  the merge service itself rather than something OTHER systems could
  register their own component-specific policy INTO, which muddled
  the two responsibilities:

    public interface StackMergePolicy {
        boolean canMerge(ItemStack a, ItemStack b);
        ItemStack merge(ItemStack a, ItemStack b);
    }

    public interface StackMergePolicyRegistry {
        void register(Identifier componentType, StackMergePolicy policy);
    }

    public final class StackMergeService {
        public static boolean canMerge(ItemStack a, ItemStack b);
        public static ItemStack merge(ItemStack a, ItemStack b);
    }

  Any component type that needs NON-DEFAULT merge behavior (Freshness
  here; the fluid contaminant/composition-bucketing fix in Section
  9b-2 uses the exact same mechanism) REGISTERS its own
  `StackMergePolicy` against the `StackMergePolicyRegistry`, keyed by
  component type. Player inventory, container shift-clicking, hoppers,
  ground-item-entity merging, machine inventories, and recipe-
  remainder handling ALL call through `StackMergeService` (which
  consults the registry) for their merge/stack-compatibility checks —
  there is no second, independent equality path anywhere that could
  silently diverge from it. This is a structural requirement on the
  implementation, not optional polish — without it, the "older state
  wins" rule is just documentation, not enforced behavior.

  ageUnits accumulation (unchanged mechanism): on any access/move/
  storage-condition change, ageUnits += elapsedTicks /
  previousPreservationMultiplier; the new multiplier only applies
  going forward (prevents the Freezer-retroactive-preservation
  exploit). The DISPLAYED/gameplay-relevant state is always just
  `stage` — precise ageUnits are purely an internal computation detail
  that determines WHEN stage transitions happen, never shown or
  compared directly.

8c. FIX: DETERMINISTIC EXACT ingredient selector matching (was
    previously a GREEDY priority algorithm, which is UNSAFE — it can
    REJECT a valid recipe. Concrete failure case: Requirement A needs
    one AROMATIC ingredient, Requirement B needs one VEGETABLE
    ingredient. An Onion matches BOTH selectors; a Carrot matches only
    VEGETABLE. If the greedy pass claims the Onion for the VEGETABLE
    requirement first — since it's processing requirements in priority
    order and Onion is a valid match — the AROMATIC requirement then
    fails to find anything, even though a valid assignment plainly
    exists: Onion->Aromatic, Carrot->Vegetable. Priority can rank
    WHICH valid solution to prefer when several exist; it cannot
    SUBSTITUTE for actually finding a valid solution in the first
    place.)
--------------------------------------------------------------------------------
  public record IngredientSelector(
          SelectorType type,     -- EXACT_ITEM, TAG, CATEGORY, TRAIT
          Identifier value
  ) {}

  public record CookingIngredientRequirement(
          IngredientSelector selector, int count,
          float qualityWeight,           -- AUTHORITATIVE weight for
                                             this recipe slot, always
                                             (see 8a's fix — this is
                                             now the ONLY source of
                                             truth for ingredient
                                             importance)
          ConsumptionTiming consumptionTiming, int priority
  ) {}

  CORRECTED MATCHING ALGORITHM — deterministic EXACT assignment, not
  greedy:
    1. Build the bipartite graph: one side is the batch's committed
       ingredient stack UNITS, the other side is the recipe's
       requirement SLOTS (a requirement needing count=2 contributes 2
       slots). An edge exists between a unit and a slot if that unit's
       CulinaryIngredientView satisfies that slot's selector.
    2. Find a MAXIMUM/EXACT matching that satisfies every slot — via
       standard bipartite matching (e.g. Hopcroft-Karp or a simple
       augmenting-path algorithm) or small backtracking search.
       Cooking recipes involve few ingredients (single digits), so
       this does NOT need to be an expensive algorithm — exhaustive
       backtracking is perfectly fine at this scale.
    3. If NO complete valid matching exists (some slot genuinely
       cannot be filled by any remaining unit under any assignment),
       the recipe cannot start / the process cannot proceed.
    4. If MULTIPLE valid complete matchings exist, `priority` (and
       any other tie-breaking heuristic, e.g. preferring to leave
       higher-grade units unclaimed for the player's other purposes)
       is used to choose AMONG the valid solutions — priority ranks
       valid outcomes, it never substitutes for the existence check
       in step 2.
    5. If the chosen matching still has meaningfully different
       equally-valid alternatives (e.g. two interchangeable Standard-
       grade Vegetable stacks), and the outcome would differ in a way
       the player would care about (different grades between
       candidates), surface an explicit CONFIRMATION/CHOICE UI rather
       than silently picking one.
    6. Ingredient CONSUMPTION only happens after a complete valid
       matching is confirmed (transactional, Section 0) — never
       partially consume for an ultimately-unsatisfiable recipe.

  tea) where the WATER REQUIREMENT'S weight climbs to 3-5 — same

  gap: `saltwater` is a trait, salt is sometimes discussed as if it
  were a contaminant, irrigation needs numeric salinity, drinking
  needs concentration, and boiling must NOT remove it — but salt
  dissolved in seawater isn't accidental contamination, it's part of
  the material's normal COMPOSITION. Treating it as a contaminant
  would make a boiling rule that "removes contaminants" accidentally
  desalinate seawater, which is wrong).

    Map<Identifier, Float> composition;   -- normal dissolved/
                                              constituent material,
                                              NOT unwanted impurities

  Example composition entries: totality:salinity,
  totality:mineral_content, totality:sugar_content,
  totality:oil_fraction — numeric, same normalized-fraction unit as
  contaminants, but semantically a DIFFERENT axis entirely.

  Four axes, four different jobs, now cleanly separated:
    Composition  -> normal dissolved/constituent material (salinity,
                     minerals, sugar, oil fraction)
    Contaminants -> unwanted impurities and hazards (drives
                     SafetyProfile via SafetyResolver)
    Traits       -> categorical properties (freshwater, magical,
                     stagnant)
    Treatments   -> processing HISTORY (boiled, filtered, distilled)

  This means a Boiling process's conditionTransferRule can correctly
  target ONLY the contaminants map (removing biological hazards)
  while leaving composition (salinity) completely untouched — the
  bug an earlier draft risked (a naive "boiling removes bad stuff"
  rule accidentally desalinating seawater) is structurally prevented
  by the axes being separate data, not just separate intent.

  Shared infrastructure across every phase: identity, amount,
  temperature, composition/traits, contaminants, storage and transfer
  (containers, tanks, pipes, pumps), machine compatibility, and
  Processing transformations (Section 7). Each PHASE module below adds
  behavior specific to that phase on top of this shared foundation —
  machines/pipes/containers do NOT need to pretend every fluid behaves
  identically.

  Player-facing Codex category can still simply be called "Liquids" if
  that reads better than "Fluid Materials" — the rename is a technical/
  architectural one, not necessarily a UI-facing one.

9b-2. FIX: fluid container/tank stacking and mixing (NEW — was a real
      gap identical in shape to the freshness stacking problem, Section
      6d: exact floating-point contaminant maps mean water gathered
      moments apart could carry e.g. biological_contamination=0.184
      vs 0.187 and refuse to stack, even though they're practically
      identical)
--------------------------------------------------------------------------------
  RESOLVED via the SAME shared StackMergePolicyRegistry/
  StackMergeService mechanism established in Section 6d — this is not a second, separately-
  invented mechanism, it's the same registry handling a second
  component type:

    - CONTAMINANT QUANTIZATION: for STACKING/equality purposes only
      (not for internal simulation), contaminant concentration values
      are rounded to a coarse bucket (e.g. nearest 0.05) before
      comparison — two containers whose contaminant maps round to the
      same buckets are stack-compatible, even if their exact
      unrounded values differ slightly. Internal/simulation values
      stay full-precision; only the STACK-COMPARISON path quantizes.
      The SAME quantization applies to `composition` values (9a's
      composition-axis fix) for the same reason.
    - TEMPERATURE: similarly bucketed for stacking purposes (e.g.
      nearest 5 degrees) rather than requiring exact float equality.
    - On MERGE (two compatible containers combining), the resulting
      contents use a deterministic combination: contaminants,
      composition, and temperature are AMOUNT-WEIGHTED AVERAGES of
      the two inputs (not "worse wins," unlike freshness — a fluid's
      contamination/composition genuinely dilutes/concentrates based
      on relative volume, whereas freshness stage doesn't work that
      way), treatments are the INTERSECTION of both inputs'
      appliedTreatments (only treatments both inputs actually
      underwent carry over — conservative, avoids incorrectly
      claiming a treatment applies to volume that never received it).

      FIX (this pass): TRAITS are NO LONGER a blanket UNION — that was
      unsafe (e.g. mixing freshwater and saltwater shouldn't produce a
      material permanently tagged as BOTH without resolving actual
      concentration; hot+cold, toxic+clean, and magical+mundane
      likewise need different combination rules depending on the
      specific trait pair, not one uniform policy). Each trait now
      declares its own MERGE STRATEGY as part of its trait definition:
        PRESERVE_IF_BOTH  -- only carries over if both inputs have it
        UNION             -- carries over if either input has it
                             (the OLD blanket behavior, now opt-in per
                             trait rather than universal)
        REPLACE           -- the merged result takes whichever input
                             contributed more volume
        CONCENTRATION_DERIVED -- computed from the numeric composition/
                             contaminant value rather than copied
                             directly (e.g. "saltwater" trait presence
                             derived from whether merged salinity
                             composition crosses a threshold, not
                             copied from either input's trait set
                             directly)
        MUTUALLY_EXCLUSIVE -- if the two inputs disagree, the merge is
                             REJECTED entirely rather than picking one
                             (forces an explicit MixingRecipe instead
                             of silently resolving the conflict)
        CUSTOM            -- resolved through a strategy registry,
                             same pattern as everywhere else in this
                             document
      Exact per-trait strategy assignments are an authoring decision
      made when each trait is defined, not a single document-wide
      default.
    - TANK MIXING (distinct from simple stacking — combining two
      DIFFERENT compatible liquids in a shared tank, not just merging
      identical-type containers): requires an explicit MIXING RULE,
      not automatic. By default, unlike materialIds REJECT mixing (a
      tank holding Water refuses an inflow of Diesel, preventing
      accidental contamination) unless a specific MixingRecipe
      (structurally similar to a ProcessingRecipeDefinition, Section
      7b) explicitly defines what combining those two produces.
      FIX (this pass): removed Wet Concrete as the example here — per
      Section 9e's clarification, Wet Concrete is a PROCESSING recipe
      (solid Cement/Aggregate + fluid Water), not an example of two
      FLUIDS mixing in a tank. A better example of genuine tank-to-
      tank fluid mixing (two fluids, no solid inputs): combining two
      compatible batches of Milk from different sources into one tank,
      or diluting a concentrated syrup with Water — both are fluid+
      fluid, unlike Wet Concrete's fluid+solid recipe. Undefined-
      combination mixing is refused by default, not silently averaged.

9c. GAS MODULE (NEW — gases are explicitly NOT treated as liquids;
    they share the Section 9a foundation but get their own behavior
    module, not folded into the Liquid module)
--------------------------------------------------------------------------------
  public record GasContents(
          Identifier materialId, long amount, float temperature,
          float pressure, Map<Identifier, Float> composition,
          Map<Identifier, Float> contaminants,
          Map<Identifier, Integer> traits
  ) implements FluidContents {}

  public record GasProfile(
          float density, float toxicity, float flammability,
          float explosiveness, float diffusionRate,
          float breathableConcentration, boolean lighterThanAir
  ) {}

  GasProfile is a phase-specific companion record for phase=GAS
  materials, linked via FluidMaterialDefinition.phaseProfileId (9a's
  attachment fix) — same pattern as LiquidDefinition for phase=LIQUID.
  NOTE: none of GasProfile's numeric fields (density, toxicity,
  flammability, explosiveness, diffusionRate,
  breathableConcentration) have an assigned unit yet — per 9a's
  narrowed units claim, these are UNSPECIFIED/TBD, not silently
  covered by the core-quantities unit list.

  GAS-SPECIFIC MECHANICS (not shared with Liquid): pressure,
  compression/expansion, diffusion through an area, rising/sinking by
  density, ventilation, breathability, toxic exposure, flammability/
  explosion risk, leakage from unsuitable pipes/tanks, condensation
  into a liquid, evaporation from a liquid into a gas. A liquid tank
  storing water needs little beyond capacity; a tank storing
  compressed gas needs pressure limits and leak/explosion behavior —
  these should NOT share identical logic, which is exactly why Gas is
  its own module rather than a Liquid variant.

  STEAM is the clearest example and should be defined as a GAS, not a
  liquid: Water -> Boiler adds heat -> Steam (gas, pressurized) ->
  pipe transport -> Turbine consumes pressure/heat -> exhaust steam ->
  Condenser -> Water. The Boiler performs an actual PHASE TRANSITION
  (liquid -> gas), not merely swapping one liquid id for another.
  Turbine energy output can depend on steam amount/pressure/
  temperature/turbine efficiency/exhaust pressure — these can be
  simplified initially, but the architecture should leave room for
  them rather than modeling Steam as "just another liquid with a fuel
  value."

  WORLD SIMULATION FOR GASES — explicitly NOT vanilla-fluid-block
  simulation by default (avoid building a full gas simulation unless
  genuinely needed, it can get expensive fast). Use whichever of these
  fits the specific gas: temporary area-cloud entities (e.g. steam
  venting from a pipe), chunk/room-based concentration values (e.g.
  poison gas filling an enclosed room), sparse gas blocks that diffuse
  and disappear, or machine-network-only substances with NO world
  simulation at all (e.g. compressed gas that only exists inside tanks
  and pipes unless deliberately released). Smoke, as an example, is
  probably better represented as particles plus an air-quality value
  than as thousands of simulated gas blocks. Oxygen/breathability at
  the world level (if ever needed) likely belongs to a future
  Environment/Atmosphere extension rather than the Gas module
  simulating it directly per-block.

9e. SLURRY MODULE (NEW — future Wet Concrete example; a pourable
    mixture that CURES/changes state over time, not an ordinary
    flowing liquid)
--------------------------------------------------------------------------------
  Example pipeline: Cement + Aggregate + Water -> [Mixing, Processing
  API, Mixer capability] -> Wet Concrete -> [Pouring, a future
  Construction/Placement system] -> Placed Wet Concrete -> [Curing,
  time + environment] -> Concrete Block.

  CLARIFICATION (this pass): this pipeline is, and has always been, a
  PROCESSING RECIPE (Cement + Aggregate are SOLID Processing inputs,
  Water is the one fluid input) — it is NOT an example of ordinary
  tank fluid-to-fluid MIXING (Section 9b-2's mixing rules). Flagging
  this explicitly because it's easy to misread as "two fluids combine
  in a tank to make a third fluid," which it isn't; Wet Concrete
  itself, once it exists, IS a fluid (phase=SLURRY), but the recipe
  that PRODUCES it belongs entirely to Processing (Section 7), the
  same as any other multi-ingredient transformation.

  Slurry-specific optional profiles (attached ONLY to slurry/curing
  materials, not every fluid):

  public record SlurryContents(
          Identifier materialId, long amount, float temperature,
          Map<Identifier, Float> composition,
          Map<Identifier, Float> contaminants,
          Map<Identifier, Integer> traits, MixtureCondition mixture
  ) implements FluidContents {}

  public record CuringProfile(
          int baseCuringTicks, float minimumTemperature,
          float maximumTemperature, boolean requiresMoisture,
          Identifier curedResultId, Identifier failedResultId
  ) {}
  CuringProfile is a phase-specific companion record for SLURRY
  materials that cure, linked via FluidMaterialDefinition
  .phaseProfileId (9a's attachment fix) — same pattern as
  LiquidDefinition/GasProfile. Not every SLURRY needs one (a slurry
  that never hardens wouldn't attach a CuringProfile at all).
  public record MixtureCondition(
          float waterRatio, float uniformity, float curingProgress,
          long mixedAt, Set<Identifier> additives
  ) {}

  OWNERSHIP SPLIT for a slurry like Wet Concrete:
    - Fluid Material API owns: identity, amount/transfer, storage,
      phase=SLURRY, temperature, composition/traits.
    - Processing API owns the Mixing transformation (Cement+Sand+
      Gravel+Water -> Wet Concrete) via the Mixer capability.
    - A future Construction/Placement system owns: pouring into the
      world, filling molds, resulting shape, reinforcement, structural
      use — NOT part of the Fluid Material API itself.
    - Environment API (Section 5) INFLUENCES curing speed — freezing
      conditions, excessive drying/heat, rain exposure, humidity can
      all affect whether/how well a slurry cures, read via the normal
      EnvironmentContext rather than any slurry-specific environment
      logic.

  SLURRIES SHOULD NOT BEHAVE LIKE ORDINARY BUCKET FLUIDS: rather than
  flowing infinitely like vanilla Water/Lava, a slurry is more likely
  transported in dedicated containers (mixer trucks, drums, tanks,
  buckets), poured into molds/designated spaces, spreads only a very
  short distance if at all, hardens after placement, may become
  unusable if left in a container too long, and can damage/clog pipes
  not designed for slurries specifically. Machines/pipes declare which
  FluidPhase values they accept (9g) — an ordinary pump might accept
  only LIQUID, while a dedicated industrial slurry pump additionally
  accepts SLURRY.

9f. ENERGY CARRIER PROFILE + MACHINE/ENERGY OWNERSHIP BOUNDARY (NEW —
    liquids/fluids used for power generation, e.g. Lava, Crude Oil,
    Diesel, Biofuel, Steam, Mana Fluid)
--------------------------------------------------------------------------------
  CORE OWNERSHIP RULE: the Fluid Material API describes the fluid AND
  its usable properties. It does NOT decide how any specific machine
  consumes it or what that machine produces — that belongs to a
  separate MACHINE/ENERGY API (referenced here by ownership boundary;
  full mechanical design of that API is future work, not part of this
  document's scope beyond the interface it needs from Fluid Material).
  A Diesel Generator, a geothermal machine, a Refinery, and a Boiler
  should NOT all read one generic `fuelValue` identically.

  FIX (this pass): EnergyCarrierProfile previously had ONE fixed
  `energyDensity` number and a `combustionProducts` field, which fits
  Diesel reasonably but doesn't cleanly describe Steam (whose usable
  energy depends on pressure AND temperature together), Lava (whose
  usable thermal energy depends on temperature relative to the
  machine's own cold-side conditions, not a flat density number), or
  a magical carrier (which may not have a "density" concept at all).
  RESOLVED via MODE-SPECIFIC sub-profiles instead of one universal
  shape:

  public record EnergyCarrierProfile(
          Set<Identifier> energyModes,
          Optional<CombustibleEnergyProfile> combustible,
          Optional<ThermalEnergyProfile> thermal,
          Optional<PressureEnergyProfile> pressure,
          Optional<MagicalEnergyProfile> magical,
          Set<Identifier> hazards
  ) {}

  public record CombustibleEnergyProfile(
          double energyDensity, Set<Identifier> combustionProducts
  ) {}
  public record ThermalEnergyProfile(
          float baseTemperature, float minimumUsableTemperature
  ) {}    -- usable thermal energy is a function of this fluid's
             temperature relative to whatever cold-side condition the
             consuming machine provides, not a flat density number
  public record PressureEnergyProfile(
          float basePressure, float expansionRatio
  ) {}    -- e.g. Steam: usable energy depends on pressure AND
             temperature together, consumed by expansion in a turbine
  public record MagicalEnergyProfile(
          double baseEnergyDensity, float instabilityRisk
  ) {}

  A given FluidMaterialDefinition only populates whichever mode-
  specific profile(s) actually apply — Diesel populates `combustible`
  only, Lava populates `thermal` only, Steam populates `pressure`
  only, Mana Fluid populates `magical` only. A machine reads the
  specific sub-profile matching its own energy mode rather than
  assuming one universal shape fits every carrier.

  Energy modes (identifiers, extensible): totality:combustible_fuel,
  totality:thermal_source, totality:volatile_fuel,
  totality:pressurized_energy_carrier (RENAMED this pass from
  `pressurized_fuel` — Steam is an energy CARRIER/working fluid, not
  "fuel" in the combustion sense, and the old name implied otherwise),
  totality:reactive_fuel, totality:magical_fuel,
  totality:radioactive_fuel.

  Examples: Lava = thermal_source (ThermalEnergyProfile populated, NOT
  treated identically to Diesel combustion). Crude Oil = combustible,
  but normally better used as Refinery INPUT than burned directly.
  Diesel = combustible_fuel (CombustibleEnergyProfile populated),
  accepted by diesel engines/generators. Gasoline-equivalent =
  volatile_fuel. Biofuel = renewable combustible_fuel. Mana Fluid =
  magical_fuel (MagicalEnergyProfile populated). Steam =
  pressurized_energy_carrier (PressureEnergyProfile populated, an
  intermediate energy carrier produced by a Boiler and consumed by a
  Turbine, per 9c).

  FIX (this pass): renamed LiquidEnergyConversionDefinition to
  FluidEnergyConversionDefinition, and replaced the culinary
  `IngredientSelector` (Section 8c) with a dedicated
  `FluidMaterialSelector` — the machine-side conversion definition
  previously depended on the CULINARY Ingredient API's selector type,
  which is wrong on three counts: it may need to select gas/molten/
  slurry inputs, not just liquids; IngredientSelector conceptually
  belongs to Cooking's ingredient-matching system (Section 8c), not
  industrial machinery; and coupling industrial machines to a Cooking-
  domain type creates an unnecessary cross-domain dependency.

  public record FluidMaterialSelector(
          Optional<Identifier> exactMaterial, Optional<FluidPhase> phase,
          Set<Identifier> requiredTraits,
          Set<Identifier> requiredEnergyModes    -- AUTHORITATIVE here
  ) {}

  FIX (this pass): removed the DUPLICATE `requiredEnergyModes` field
  that previously existed on BOTH `FluidMaterialSelector` AND
  `FluidEnergyConversionDefinition` — two places asserting the same
  requirement risked disagreement. `FluidMaterialSelector.
  requiredEnergyModes` is now the SOLE authority for which energy
  modes a conversion accepts; `FluidEnergyConversionDefinition` no
  longer repeats it.

  FIX (this pass): added `conversionModelId`, a machine-side
  CONVERSION STRATEGY identifier, alongside (not replacing) the simple
  flat-output fields — a fixed `baseEnergyProduced` number works fine
  for a simple combustion generator, but conflicts with the mode-
  specific profiles from 9f: Steam's real output depends on actual
  PRESSURE and TEMPERATURE together, Lava's usable thermal energy
  depends on its CURRENT temperature relative to the machine's own
  cold-side conditions, compressed gas depends on EXPANSION, and a
  magical fluid's output may depend on its INSTABILITY. A single
  static number can't represent any of those relationships — the
  strategy identifier lets the machine actually READ the fluid's real
  FluidContents/profile data and compute output dynamically instead.

  public record FluidEnergyConversionDefinition(
          Identifier id, FluidMaterialSelector materialSelector,
          long amountConsumed,
          Identifier conversionModelId,     -- e.g. totality:combustion,
                                                totality:thermal_gradient,
                                                totality:pressure_expansion,
                                                totality:magical_conversion
                                                — resolved through a
                                                strategy registry that
                                                reads the actual
                                                FluidContents + machine
                                                operating conditions
          Optional<Long> baseEnergyProduced,  -- still available as a
                                                  SIMPLE FALLBACK for
                                                  straightforward fuels
                                                  (e.g. plain
                                                  totality:combustion
                                                  can just use this
                                                  flat number), but is
                                                  NOT the universal
                                                  model — dynamic
                                                  strategies compute
                                                  their own output
                                                  instead of reading
                                                  this field at all
          float conversionEfficiency,
          List<IndustrialOutput> byproducts,
          MachineOperatingConditions conditions
  ) {}

  Examples: Diesel Generator accepts anything tagged
  combustible_fuel, but gets its best efficiency specifically from
  Diesel — uses `totality:combustion` with a simple
  `baseEnergyProduced` fallback. Lava Generator accepts
  thermal_source, uses `totality:thermal_gradient` reading Lava's
  actual current temperature. Boiler accepts suitable heating fuels
  and converts Water into Steam (a phase transition + machine action,
  not a simple fuel burn). Steam Turbine consumes Steam via
  `totality:pressure_expansion`, reading actual pressure/temperature
  rather than a flat number. Magical Generator accepts magical_fuel
  via `totality:magical_conversion`, factoring in instabilityRisk.
  Refinery does NOT generate energy directly — it PROCESSES Crude Oil
  into Diesel and other outputs (this transformation belongs to the
  Processing API, Section 7, exactly like any other Wheat->Flour-style
  transformation; oil refining is not a special case).

  CONTAMINANTS MATTER INDUSTRIALLY TOO: fluid condition can influence
  energy efficiency, machine wear, soot/residue, clogging, explosion/
  fire chance, toxic emissions, byproduct quantity, or whether a
  machine accepts the fuel at all. Example: Clean Diesel operates
  normally; Contaminated Diesel produces less energy and damages the
  generator; water-contaminated fuel may cause outright failure;
  impure Lava may leave slag; an unstable magical liquid might
  generate MORE energy but risk a malfunction (tracked via
  `instabilityRisk` on MagicalEnergyProfile above). The existing
  contaminants system (9b) stays useful well outside Survival/Cooking
  — same map-based hazard representation serves both domains.

  OTHER INDUSTRIAL FLUID ROLES (extension points, not required now):
  coolant, lubricant, hydraulic fluid, cleaning solvent, chemical
  reagent, heat-transfer fluid, waste fluid. These can be expressed as
  namespaced traits or specialized machine-use profiles later — the
  API should not assume every non-drinkable fluid exists only as a
  Cooking ingredient.

10c. Growth model — cheap, AGE + CARE only on ordinary field crops

10f. FIX: genetics scalability — detailed genome data does NOT live
     on every field crop block (was a real contradiction: "ordinary
     crops use only 2 small values" directly conflicted with
     individual plants also being expected to carry a full genome,
     stability, generation, parents, multiple stats, and potential
     traits — storing that per block entity across a large field would
     be expensive)
--------------------------------------------------------------------------------
  FOUR-TIER DATA MODEL (resolves the contradiction):

    1. SEED ITEMS carry the FULL genetic profile — genome code,
       stability %, stat bars (Vigor/Productivity/Resilience/Culinary
       Potential or whatever final stat list is chosen), known traits
       with tiers, locked/potential traits. This is fine because seeds
       are individual ITEMS in an inventory, not thousands of
       simultaneous block entities.

    2. EXPERIMENTAL/UNSTABLE GENETICS are only grown in dedicated
       Breeding Beds, planters, or specialized greenhouse plots — a
       small, deliberately limited number of locations that CAN afford
       to carry detailed per-plant genetic data, because there are
       never thousands of them at once.

    3. STABILIZED CULTIVARS growing in ORDINARY FIELDS carry only a
       COMPACT CULTIVAR REFERENCE (an Identifier pointing at a
       registered cultivar definition) PLUS the existing cheap Age+Care
       values — NOT the full genome. This is what keeps large-scale
       farming performant: a field of 10,000 wheat plants all
       reference the same lightweight cultivar id, none of them
       individually carry a genome.

    4. The full genetic profile for a STABILIZED cultivar lives in the
       Codex's Cultivar sub-section (Section 4f) as ONE registered
       record per cultivar (not per plant) — generation, stability,
       stats, traits, creator, parent lines all stored once, referenced
       by every field crop of that cultivar via its compact id.

  Tools (unchanged from earlier draft, now understood to operate on
  tier 1/2 data specifically): Pollination Brush (collect pollen from
  mature crops), Seed Analyzer (decode a seed's genome), Breeding Bed
  (combine two parents' pollen, produce new seeds with inherited
  traits), Greenhouse (controlled environment for tier-2 experimental
  growing).

  Progression: Wild (low stats, high variation) -> Gen 1 Selected ->
  Gen 2 Improved -> Gen 3 Stabilized -> named Elite Cultivar. Once
  STABILIZED, a cultivar graduates from tier-2 (detailed, per-plant) to
  tier-3/4 (compact reference + Codex registry) representation — this
  transition is the actual mechanical meaning of "stabilizing."

  NOTE: the genetics system's own Trait Rarity ladder (seen in the
  reference mockup as Common/Uncommon/Rare/Epic/Legendary) is SEPARATE
  from both Cooking's FoodQuality/tier naming (Section 17f) and
  Product Condition's ProductGrade (Section 6a) — three different
  ladders, three different jobs. Do not conflate them.

13a. Survival's ownership model (RECONSTRUCTION — PROPOSED, from
     recovered boundaries — needs sign-off before canonical)
--------------------------------------------------------------------------------
  Survival COORDINATES self-care consequences WITHOUT duplicating the
  authorities of its source systems:
    - Environment (Section 5) owns current world conditions.
    - Fluid Material (Section 9) owns liquid identity, composition,
      treatment, contamination, temperature, and culinary freshness/
      grade where applicable.
    - Thirst (13b) owns the player hydration resource.
    - Temperature (13c) owns body-temperature consequences.
    - Rest (see TOTALITY_REST_AND_FATIGUE.txt) owns rest sessions and
      recovery.
    - Diet (Section 12) owns dietary history and nutrition status.
    - Exposure (a future/shared concept, see TOTALITY_SHARED_CROSS_

      hazards.

      hold — not before.
    - Survival itself can provide shared HUD/presentation, difficulty
      settings, and cross-system consequence coordination.

  DO NOT create one generic "Survival condition" component that
  replaces all of these — each listed system keeps its own authority,
  Survival just coordinates the player-facing experience across them.

--------------------------------------------------------------------------------
13b. Thirst
--------------------------------------------------------------------------------
  RECOVERED — ADOPTED.

  RESOURCE: Thirst drains slowly over time. Drains FASTER from: verbal-
  component spellcasting, repeated verbal casting in a short period,
  desert conditions, extreme heat, and rest periods (the player goes
  without drinking while resting).

  WATER RISK: drinking normal untreated water restores Thirst but CAN
  apply a negative effect. Ocean/seawater has GREATER negative risk and
  can be dehydrating because salinity is COMPOSITION, not merely
  contamination (matches the Fluid Material API's composition-vs-
  contaminants axis split, Section 9a). Purified Water avoids/reduces
  ordinary contamination risk. Other drinks can restore Thirst and
  provide authored effects.

  IMPORTANT: fluid safety MUST come from `LiquidContents.contaminants()`
  and the shared Safety resolver (Section 6b/9b) — Thirst must NOT
  maintain a competing water-purity truth of its own. This is the same
  "one authority per axis" discipline already locked in elsewhere in
  this document.

  PENALTY IDENTITY: Thirst penalties primarily affect Spellcasting,
  Mana, and Verbal-component use — intentionally DISTINCT from extreme
  heat, which primarily affects Stamina (13c).

  REST INTERACTION: Long Rest does NOT refill Thirst — it CAUSES some
  Thirst loss. Short Rest also causes Thirst loss. Duration/activity
  can change the amount. Exact values TBD.

  ENVIRONMENT DEPENDENCY: Thirst V1 may use a neutral heat modifier
  before Environment (Section 5) fully exists. Once EnvironmentService
  exists, heat/desert modifiers MUST read it rather than implementing
  a private temperature check (matches the build-order note already in
  Section 2 about Thirst's heat modifier being a no-op until
  Environment core is in place).

  TBD: exact drain rates and rest-related loss amounts.

--------------------------------------------------------------------------------
13c. Temperature
--------------------------------------------------------------------------------
  RECOVERED — ADOPTED.

  PRESENTATION: a state-based indicator rather than a normal numeric
  bar. Hot states use red visual language, cold states use blue visual
  language.

  RESISTANCE: END provides a small contribution. Clothing WARMTH is
  the PRIMARY lever — wearable items receive Warmth according to type/
  material. Food can temporarily increase Warmth or provide cooling
  (Ice cream was the recovered example of a cooling food).

  CONSEQUENCES: extreme heat primarily drains/penalizes STAMINA. Cold/
  freezing primarily damages/threatens HEALTH. Extreme heat ALSO
  increases Thirst drain (13b) — this is the cross-reference point
  between the two systems.

  All world-condition input comes from EnvironmentService (Section 5)
  — Temperature does not independently sample world state.

  TBD: state thresholds; drain and damage rates; wetness/wind-chill
  formulas; layering rules; shelter modifiers; species resistances;

17e. FIX: ONE authoritative quality algorithm (was previously two
     competing formulas in an earlier draft — one blended-score
     approach and one separate tier-adjustment-table approach — that
     would have produced inconsistent results depending on which got
     implemented; see the archive for that earlier draft's exact
     wording, it's not worth reproducing here since it's superseded)
--------------------------------------------------------------------------------
  THE authoritative pipeline (the STRUCTURE below — one pipeline, one
  set of steps, run in order — is what's actually LOCKED; the numeric
  values used at each step are DEFAULTS for playtesting, not final
  balance):

    1. Compute ingredient potential: weighted average of the batch's
       committed ingredients' ProductGrade (Section 6a), using each
       requirement's qualityWeight (Section 8c/8d, authoritative on
       the REQUIREMENT per the fix there). Normalize to a fixed
       numeric range (e.g. 0-100, exact range TBD).
    2. Compute execution score: average roll margin across all
       completed processes in the batch (roll total minus DC per
       process, averaged), normalized to the SAME numeric range.
    3. Combine into finalScore via a blend of ingredientScore and
       executionScore. CURRENT DEFAULT (starting point for
       playtesting, NOT locked): finalScore = 0.6 x ingredientScore +
       0.4 x executionScore. The REQUIREMENT that there be exactly
       ONE authoritative blend formula (not two competing ones) is
       locked; the specific 60/40 split is not — adjust freely during
       balance passes without needing to revisit this document's
       structure.
    4. Convert finalScore into a preliminary quality tier via authored
       score-to-tier breakpoints — PLACEHOLDER example only, e.g.
       roughly 0-20 Poor, 21-45 Standard, 46-70 Fine, 71-90
       Exceptional, 91-100 Masterpiece (tune during playtesting). This
       step NEVER produces RUINED directly — see the Ruined
       reconciliation note below; Ruined comes from a separate
       explicit signal, not from scoring low.
    5. Apply the recipe's own quality CEILING (Section 17h) — clamp
       down if the preliminary tier exceeds what this specific recipe
       can ever produce.
    6. Apply the ELEVATION CAP (below) — clamp how far execution alone
       was allowed to lift the result above what ingredients alone
       would produce.
    7. Resolve SAFETY independently (Section 17f) — this NEVER factors
       into the quality tier calculation above; it's a fully separate
       resolution running in parallel, and — per 17f's fix — is NEVER
       overridden by step 8 either.
    8. Check for any SPECIAL COMPLETION RULES the recipe registers
       (Section 17j) — these can override the QUALITY TIER, output
       item, and presentation for specific authored outcomes (Doorstop
       Loaf, Perfectly Executed, etc), but explicitly CANNOT override
       the Safety result from step 7 (17f).

  RUINED RECONCILIATION (was a real gap — an earlier draft had THREE
  potentially-disagreeing signals for whether a dish is Ruined: a
  `ruined: boolean` field on the batch component, `DishQuality.RUINED`
  as an enum value, and a vague "Ruined-adjacent" entry in the score-
  breakpoint table above). ONE RULE, now locked: the batch's explicit
  `ruined` boolean (set by the roll-outcome/flaw system during
  processing, Section 17c/17k) is the SOLE trigger for
  `DishQuality.RUINED` on the finished dish. The numeric score-to-tier
  conversion in step 4 above ONLY EVER produces POOR through
  MASTERPIECE — it never independently decides Ruined. If
  `ruined=true`, steps 4-6 are skipped entirely and the dish resolves
  as RUINED regardless of what the score would otherwise have been.

  ELEVATION CAP (DEFAULT/recommended, applies at step 6, exact numbers
  are playtesting starting points not a final balance guarantee):
  normal execution can raise the result AT MOST 1 tier above what
  ingredients alone would produce; masterful execution AT MOST 2
  tiers. Bad execution has NO equivalent floor protection by default —
  it can reduce quality freely. Cooking down is easier than cooking
  up, by design; exact cap numbers are tunable.

17f. FIX: Safety is fully independent from Quality, with its own
     explicit resolver (was contradicted by an earlier draft that both
     said "quality and safety are separate" AND listed "contaminated"
     as an example of the Ruined quality tier — a real internal
     contradiction)
--------------------------------------------------------------------------------
  CORRECTED RULE: contamination/toxicity does NOT automatically force
  Ruined quality. A dish CAN legitimately be "Quality: Masterpiece,
  Safety: Toxic" — flawlessly executed using dangerous ingredients.
  Whether a SPECIFIC recipe treats unsafe results as automatically
  unusable (e.g. "this dish becomes inedible if Contaminated") is an
  AUTHORED PER-RECIPE RULE, not a global engine behavior.

  Safety resolver (parallel to, and independent of, 17e's quality
  pipeline; updated this pass to match 17a-2's per-process,
  per-axis condition transfer fix):
    1. Gather every committed ingredient's SafetyProfile (Section 6b),
       forming the batch's starting hazard set — PRESERVE_WORST is the
       sensible default combination for the starting set (one
       contaminated ingredient taints the whole dish).
    2. Walk the batch's processes IN ORDER. For each process that
       declares a `conditionTransfer` policy (Section 17a-2), apply
       its `safetyRule` specifically to the current hazard set — e.g.
       a Boiling process's safetyRule removes biological-contaminant
       entries specifically, leaving salt/magical-toxin entries
       untouched. (That same process's `conditionTransfer` may ALSO
       carry a `traitRules`/`nutritionRule`/etc affecting other axes —
       this resolver only concerns itself with `safetyRule`.)
       Processes with no `conditionTransfer` at all leave the hazard
       set unchanged (most processes — Assembly, Baking without a
       purification purpose, etc. — simply pass condition through).
    3. The resulting SafetyProfile (after all processes have been
       applied) attaches to the finished dish, independent of whatever
       quality tier it landed on.

17l. FIX: full batch persistence/cancellation/ownership rules (was
     entirely unaddressed previously — a real gap for a multiplayer-
     safe implementation)
--------------------------------------------------------------------------------
  EXPLICITLY DEFINED (not left to be discovered during implementation):

    - CANCELLATION: player-initiated cancel returns whatever
      ingredients are still "intact" per the batch's current flaw
      state — exact return policy (full refund vs. partial, given
      some ingredients may already be transformed) is a per-recipe or
      global default decision, TBD, but the RULE that cancellation
      must be explicitly handled (not just "delete the batch") is
      locked in.
    - ATOMIC ITEM CONSUMPTION: ingredient consumption for starting a
      batch is transactional (Section 0 global convention) — no
      partial consumption if the full requirement set can't be
      satisfied.
    - STATION BROKEN MID-PROCESS: since the batch (intermediate item)
      is the source of truth (Section 17d's capability model + the
      batch component itself), breaking the physical station block
      must NOT destroy or duplicate the batch's data — the batch
      persists as an item, independent of the station that was being
      used, consistent with "batch is source of truth."
    - LOGOUT/DEATH: batch state persists on the item exactly as any
      other item would (inventory-based, standard persistence) —
      define explicitly whether death drops it normally (yes, by
      default, same as any other held/inventory item) or has special
      handling (no special handling by default).
    - FERMENTATION/WAIT PHASES CONTINUING "OFFLINE" (FIX this pass —
      clarified wording, was ambiguous about what "offline" meant):
      since readyAtTick uses a stable SERVER timeline (17k), a wait
      phase continues accumulating correctly whenever the SERVER is
      running, REGARDLESS of whether the specific PLAYER who owns the
      batch is currently connected — a batch left cooking while its
      owner is logged off still progresses normally as long as the
      server itself stays up. This does NOT mean progress continues
      through an actual SERVER SHUTDOWN — a server tick count does not
      advance while the server process itself isn't running, so a
      batch's wait phase correctly PAUSES across a full server
      restart, unless wall-clock (real-world) time is DELIBERATELY
      used instead of tick count for that specific purpose (not the
      default; would need to be an explicit per-recipe or per-system
      choice if ever wanted).
    - DIMENSION TRAVEL: moving between dimensions must NOT desync a
      wait-phase timer, which is why 17k mandates a stable timeline
      model rather than anything tied to a specific dimension's clock.
    - DUPLICATION PREVENTION: copying or moving a batch item (via
      inventory manipulation, hoppers, dupe-bug-adjacent interactions)
      must NOT duplicate its captured ingredients or roll history —
      explicit acceptance test, Section 0a.
    - COLLABORATIVE COOKING (PROPOSED V1 policy, not an unquestionable
      permanent architectural rule): batches default to OWNER-LOCKED —
      only the creatorId can advance it through further processes.
      Another player continuing someone else's batch is NOT supported
      in this proposed V1 (could become a future mastery/multiplayer
      feature, and the underlying batch-as-source-of-truth design
      doesn't preclude revisiting this default later).
    - AUTOMATION: whether an automated system (future hopper-fed
      station, etc.) can advance a batch is a per-station-tier
      decision (consistent with the Electrical-tier-vs-base-tier
      pattern already established) — but per Section 0's global
      convention, automated completion does NOT award player XP,
      Codex discoveries, or records by default.

18. QUEST PRESENTATION AND MARKER SYSTEM (NEW — planned future
    functionality, NOT required for current API implementation)
================================================================================
STATUS: this is a DESIGN for later. Treat everything in this section
as planned, not something Claude Code needs to build alongside the
foundational APIs above. It's included now so the design exists
before it's needed, and so First Loaf (Section 19) can be written
against its final trigger model without contradicting it later.

--------------------------------------------------------------------------------
18a. Three separate concepts (do not conflate them)
--------------------------------------------------------------------------------
  QUEST CATEGORY determines color/visual identity.
  QUEST STATE determines available/advance/turn-in presentation.
  DISPLAY PRIORITY/WEIGHT determines which marker wins when one NPC
    has several relevant quests at once.

  Quest marker COLOR represents CATEGORY, not narrative importance by
  itself. Gold usually wins over purple/green because Main Story has
  the highest DEFAULT weight — not because gold is hardcoded to always
  override every other color. Individual quests can override their
  category's default weight (e.g. an urgent personal-danger follower
  quest might outrank an ordinary main-story conversation).

--------------------------------------------------------------------------------
18b. Quest category (registry-based, extensible — do not hardcode
     every future color into the NPC renderer)
--------------------------------------------------------------------------------
  public record QuestCategoryDefinition(
          Identifier id, Text displayName, int color,
          Identifier markerStyle, int defaultDisplayPriority
  ) {}

  Initial categories: totality:guide (Green), totality:main_story
  (Gold), totality:follower (Purple). Future categories can share a
  color while differing by marker STYLE (border/glow/particle/emblem)
  rather than needing a unique color each — e.g. totality:side_story,
  totality:profession, totality:faction, totality:world_event,
  totality:repeatable, totality:daily, totality:bounty,
  totality:romance are all anticipated future categories, none
  required for V1.

  Follower quests (purple): recruitment, relationship progression,
  personal story resolution, follower ability unlocks, loyalty/
  approval changes — kept under one broad FOLLOWER category by
  default, with an optional QuestArcType (RECRUITMENT vs PERSONAL)
  sub-distinction if they diverge enough mechanically to warrant it
  later, without needing a whole new top-level category yet.

--------------------------------------------------------------------------------
18c. Quest state / interaction symbol (separate from category color)
--------------------------------------------------------------------------------
  public enum QuestInteractionState { AVAILABLE, READY_TO_ADVANCE,
      READY_TO_COMPLETE, ACTIVE_DIALOGUE }

  Suggested symbol mapping (V1 can use just "!" for everything if
  simpler symbols aren't ready, but the state enum should still exist
  underneath so a later visual pass doesn't require a data model
  change): "!" = available, "?" = ready to complete, a smaller
  dot/diamond/outlined symbol = active-but-not-completing interaction
  available.

--------------------------------------------------------------------------------
18d. Priority/weight resolution + recommended default ordering
--------------------------------------------------------------------------------
  public record QuestMarkerCandidate(Identifier questId,
      Identifier categoryId, QuestInteractionState state,
      int displayPriority) {}

  Suggested default priority tiers:
    QuestImportance: GUIDE(10), SIDE(20), PROFESSION(30),
      FOLLOWER(70), MAIN_STORY(100)
    (Exact middle-tier values/categories can change later; every quest
    source exposes an importance value regardless.)

  Recommended resolution order when an NPC has multiple candidates
  (playtesting decision, not fully locked): main-story turn-in >
  main-story available > other quest turn-in > major side/profession
  available > guide turn-in > guide available > in-progress
  interaction. Whether "ready to complete" should generally outrank
  "available" across DIFFERENT categories (e.g. a guide turn-in
  outranking an unstarted main-story quest) is an explicit open
  playtesting/UX decision, not resolved here.

--------------------------------------------------------------------------------
18e. Per-player resolution (NOT stored on the NPC entity)
--------------------------------------------------------------------------------
  public final class QuestMarkerService {
      public static Optional<ResolvedQuestMarker> resolve(
              ServerPlayerEntity player, Entity questSource);
  }

  MUST be resolved PER PLAYER — one player may see a gold marker,
  another a green one, another nothing, since quest progression is
  per-player. The NPC entity must NOT store one universal visible
  marker. The client only receives the final RESOLVED marker for that
  specific player, never the underlying private quest-condition data.

--------------------------------------------------------------------------------
18f. Dialogue menu shows EVERY eligible line with its own color
     (independent of which single marker is shown overhead)
--------------------------------------------------------------------------------
  Example:
    [!] We need to discuss the dimensional breach.     (Gold)
    [!] I need your help with something personal.       (Purple)
    [!] Could you teach me how to bake?                 (Green)
        Show me what you are selling.
        Goodbye.

  The overhead marker only attracts the player to the NPC; the FULL
  choice set becomes visible once dialogue is actually opened. A gold
  overhead marker does not hide the fact that green/purple options
  also exist inside the conversation.

--------------------------------------------------------------------------------
18g. Visibility/clutter management
--------------------------------------------------------------------------------
  Markers visible only within a reasonable distance, fading at longer
  range; hidden through solid walls by default (unless a future
  tracking effect/ability permits otherwise); positioned above the
  nameplate without clipping into ceilings; main-story markers can
  pulse/be more visually prominent, guide markers stay calmer/static;
  markers suppressed for quests still hidden by unmet prerequisites; a
  future phone setting for marker visibility is a reasonable later
  addition, not required now.

--------------------------------------------------------------------------------
18h. Accessibility — do not rely on color alone
--------------------------------------------------------------------------------
  Since many categories will eventually exist, pure color-only
  distinction becomes harder to read. Keep the base "!" silhouette
  recognizable, but vary SECONDARY presentation per category: gold
  main story gets a stronger glow/angular frame, purple follower gets
  a softer aura/companion-shaped border, green guide gets a book-
  shaped frame, a repeatable quest gets a circular-arrow border, a
  timed world event pulses its outer ring, a daily quest gets a small
  clock/sun detail.

--------------------------------------------------------------------------------
18i. Weight/priority is a SHARED concept, not just a renderer detail
--------------------------------------------------------------------------------
  The same priority value should later also drive: dialogue line
  ordering, quest log sorting (phone app), phone notifications, map-
  marker prominence, HUD tracking suggestions, and whether an NPC
  surfaces in a future "Nearby Quests" list — one shared importance
  concept feeding several presentation surfaces, not reimplemented per
  surface.

19. FIRST LOAF QUEST (REWRITTEN against the current Cooking API —
    supersedes the archived version entirely)
================================================================================
--------------------------------------------------------------------------------
19a. Trigger — CORRECTED (was: "first dialogue with the Chef." Now:
     an OPTIONAL guide quest, selected deliberately, not automatic)
--------------------------------------------------------------------------------
  First Loaf is a GREEN [!] GUIDE quest (Section 18b), consistent with
  the established Banker guide-quest pattern. It does NOT trigger
  automatically on first meeting the Chef/Baker NPC and is NOT an
  early-game forced onboarding gate. It begins ONLY when the player
  actively selects the marked green guide-dialogue line, e.g.:

    [!] Could you teach me how to bake?          (rendered green)

  Selecting this does NOT instantly accept the quest — it opens a
  quest-OFFER sub-dialogue first:

    Baker: "I can teach you the basics, but flour and yeast don't
    grow on shelves. I can provide what you need for a small fee — or
    you can bring your own."

    > Accept the lesson.
    > I'll bring my own ingredients.
    > Maybe another time.

  The player retains full control over whether/when to start.

--------------------------------------------------------------------------------
19b. Existing-progress awareness (new — the quest should not pretend
     this is necessarily the player's first-ever cooking experience)
--------------------------------------------------------------------------------
  A player CAN cook Bread independently (via improvised/unlearned
  attempts, Section 17's roll system) and never take this quest at
  all, or take it AFTER already having cooked several dishes, purely
  for the reward/dialogue/formal teaching rather than as a true
  tutorial. If the player already has some Bread-cooking history when
  they select the guide line, the Baker's dialogue should acknowledge
  it rather than pretending total ignorance, e.g.:

    Baker: "You already know your way around dough. Still, I may be
    able to teach you a more reliable method."

  In that case the quest can function more as a shorter proficiency
  DEMONSTRATION than a from-scratch tutorial — exact dialogue
  branching TBD, but the PRINCIPLE (detect existing progress, adjust
  tone) is locked in and applies to other future guide quests too
  (e.g. the existing Banker guide quest should follow the same
  philosophy: teach and validate, but don't condescend to a player who
  already knows the system).

--------------------------------------------------------------------------------
19c. Objectives — CORRECTED against the current Bread process
     sequence (was: Mix -> Knead -> Shape -> Score -> Bake, a 5-step
     sequence from the archived design. Now: matches Section 17's
     actual adopted process definitions)
--------------------------------------------------------------------------------
  1. Obtain the Bread ingredients (from the Chef, per the Persuasion
     outcome below, or gathered independently).
  2. Start a Bread batch UNDER THE CHEF'S GUIDANCE (see 19e on the
     GUIDED knowledge state).
  3. Mix and knead the dough (single combined objective in the UI,
     even though these are two separate rolled processes underneath).
  4. Allow the dough to ferment (a WAIT PHASE per Section 17k, not a
     rolled process — the UI should reflect this as a countdown, same
     pattern as any other fermentation/proofing phase).
  5. Bake the loaf.
  6. Return YOUR OWN loaf to the Chef.

  Shape/Score, if ultimately retained as OPTIONAL modifiers (per the
  "optional presentation-improving DEX check" framing discussed
  earlier in this design process — see the archive for the original
  phrasing — rather than mandatory steps), are NOT quest objectives —
  the quest only tracks the mandatory process sequence defined on the
  CookingRecipeDefinition (17a-2). The quest implementation must read
  process events GENERICALLY (see 19d) rather than hardcoding process
  names, so if the underlying Bread recipe's exact step list changes
  later, the quest doesn't silently break.

--------------------------------------------------------------------------------
19d. FIX: progress binds to a SPECIFIC BATCH, not inventory possession
     (was a real exploit surface in the archived design — advancing
     objectives by simply checking "does the player HAVE Flour/Dough/
     Bread" would let a player buy an existing loaf, receive one from
     another player, use an old loaf, drop-and-repickup an
     intermediate item, or progress using several unrelated batches
     simultaneously)
--------------------------------------------------------------------------------
  On accepting the quest offer (19a), store:
    questId, playerUuid, batchId (assigned once the tutorial batch
    actually starts, not before), recipeId, attemptNumber

  The quest listens to GENERIC Cooking events, not ad-hoc inventory
  checks:
    BATCH_STARTED, PROCESS_COMPLETED, BATCH_READY, BATCH_RESOLVED,
    DISH_TURNED_IN

  and filters for events where the batch's ID/creator matches what
  was stored. If the original tutorial batch is Ruined, the player can
  start a NEW batch of the same recipe and the quest tracks that new
  batchId instead (does not require the FIRST attempt specifically to
  succeed) — but the eventual turn-in loaf must trace back to a batch
  created by the player AFTER accepting this quest, using the correct
  recipe, by the correct creator.

--------------------------------------------------------------------------------
19e. FIX: temporary GUIDED knowledge state (was: the archived design
     had the Chef "offer to teach baking" narratively, but permanent
     recipe knowledge was only granted AFTER completion — meaning the
     story and the mechanics disagreed about whether the player was
     actually being taught during the quest itself)
--------------------------------------------------------------------------------
  Three-state model for recipe knowledge (extends the existing known/
  unknown distinction):

    UNKNOWN -> GUIDED -> LEARNED

  UNKNOWN: normal improvised-attempt rules apply (Disadvantage or
    whatever the current unlearned-recipe roll modifier is under
    Section 17b).
  GUIDED (active only while this specific quest is in progress): the
    Bread process steps are made VISIBLE (no silhouette/"?" hiding),
    the Chef provides tutorial prompts, and quest guidance REMOVES the
    unknown-recipe roll penalty for the DURATION of the quest — this
    makes "the Chef teaches you to bake" mechanically true during the
    lesson itself, not just narratively true after the fact.
  LEARNED (permanent, granted on successful turn-in): full permanent
    recipe knowledge exactly as the existing learned-recipe system
    already defines it (Section 17b's normal roll bonus for known
    recipes).

--------------------------------------------------------------------------------
19f. Access to stations during the quest (PROPOSED — was previously
     unaddressed friction; this specific solution not independently
     confirmed by Stefan this pass)
--------------------------------------------------------------------------------
  The Bakery contains CHEF-OWNED tutorial stations (Mixer, Flat
  Surface/Work Surface, Oven) the player may use WHILE THIS QUEST IS
  ACTIVE, rather than requiring a brand-new player to build an entire
  personal kitchen just to complete their first cooking tutorial.
  Crafting one's own stations remains the normal route for independent
  cooking afterward — this is purely a quest-scoped convenience, not a
  permanent station grant. TBD: exact access mechanism (temporary
  permission flag, dedicated quest-only station instances, etc).

--------------------------------------------------------------------------------
19g. Persuasion roll for ingredients — SAFEGUARDED against soft-locks
     (was: a Nat 1 simply raised the price with no fallback, which
     could soft-lock a brand-new player with zero credits)
--------------------------------------------------------------------------------
  Nat 1 (PROPOSED, not independently confirmed by Stefan this pass):
    price increase is CAPPED/limited (not unbounded), AND the Chef
    offers an alternative — either a small ingredient-gathering
    objective the player can complete instead of paying, or the Chef
    extends credit and deducts the cost from the eventual quest
    reward. Exact mechanism TBD. The one CONFIRMED requirement (this
    part is locked): a new player must always be able to progress
    somehow — no path that can hard-soft-lock a zero-credit new
    player on this specific roll.
  Normal fail: pay full price (unchanged).
  Success: free ingredients (unchanged).
  Nat 20 (PROPOSED, not independently confirmed by Stefan this pass):
    gives an EXTRA COMPLETE INGREDIENT SET (a free retry's worth of
    materials) rather than a single higher-grade ingredient — the
    REASONING (avoid a lucky Persuasion roll distorting the tutorial's
    quality outcome via inflated ingredient grade) is sound, but the
    exact reward mechanic itself is a content/reward decision for
    Stefan to confirm, not something locked by this design pass.

--------------------------------------------------------------------------------
19h. Turn-in validation (expanded — now checks safety too, per
     Section 17f)
--------------------------------------------------------------------------------
  1. Correct recipe (Bread).
  2. Created by the player themselves (via the bound-batch tracking
     in 19d).
  3. NOT Ruined.
  4. SAFETY is acceptable (per Section 17f's independent safety
     resolver — the Chef should reasonably refuse a beautiful loaf
     made with toxic water; this is a good early, low-stakes moment to
     quietly teach the player that safety and quality are separate
     systems).
  5. The batch was created AFTER accepting this quest (quest-bound,
     per 19d).

  Doorstop Loaf turn-in: REJECTED with a dedicated snarky/horrified
  Chef reaction, objective does not complete — go make real Bread. Not
  a quest FAIL, just "wrong item."

  FIX: NARROWED the overly broad "no Totality quest can actually
  fail" claim from an earlier draft — that was stated as if it were a
  universal engine rule, but only the ARCHIVED Cooking design actually
  established that THIS tutorial specifically shouldn't be
  permanently failed by a cooking mistake. It never decided that NO
  future Totality quest can ever have a real failure state, branching
  failure outcome, time limit, or alternate ending. CORRECTED RULE
  (scoped to what was actually decided): First Loaf, and ordinary
  guide quests generally, are not permanently failed by an unsuccessful
  attempt. This says nothing about main-story, follower, or other
  future quest categories (Section 18b) — those may absolutely have
  real failure/branching consequences if that's the right design for
  them later.

--------------------------------------------------------------------------------
19i. Rewards — SUGGESTED/PROPOSED (analysis of why the archived
     design's reward was risky is sound reasoning, but the specific
     replacement below is a recommendation, not something Stefan has
     independently confirmed — treat every specific in this
     subsection as TBD pending his sign-off)
--------------------------------------------------------------------------------
  Normal completion: Bread recipe becomes LEARNED (19e), small Cooking
    XP, possibly starter credits (defer exact amount to economy
    balancing).

  "Perfectly Executed" Bread turn-in (Section 17j's special
    completion, name pending Ambrosia resolution per 17g): SUGGESTED —
    astonished Chef dialogue + a cosmetic title. The REASONING for
    toning this down is solid: the archived design's reward (special
    dialogue + title + a PERMANENT shop discount, all granted from an
    extremely rare roll during literally the player's FIRST tutorial)
    makes an astronomically rare outcome economically important enough
    that a player who knows about it might refuse to ever turn in
    ordinary bread and grind for the secret result instead — which may
    or may not be an intentional design goal, but should be a
    CONSCIOUS decision rather than an accident of how the quest was
    originally scoped. SUGGESTED revision: the permanent Chef discount
    is REMOVED from this specific quest's reward and instead becomes
    available from ANY genuinely Perfectly-Executed Bread produced
    later (in-quest or not) — OR, if a permanent discount specifically
    tied to this quest is still wanted, keep it small (e.g. 5%) rather
    than the original unspecified/larger discount. Also acceptable: a
    cosmetic bakery decoration or a bonus recipe unlock instead of an
    economic reward, avoiding the economy-distortion problem entirely.
    Exact final choice TBD/Stefan's call — the CONSTRAINT (don't make
    the tutorial's rarest outcome a big permanent economic lever) is
    locked in.

  Narrative flag: chef_first_loaf_complete — prevents re-trigger,
    unlocks a Chef callback line afterward. (Persuasion roll outcome
    stays a one-off with no lasting flag, as originally decided.)

--------------------------------------------------------------------------------
19j. Do not hardcode "Ambrosia" (explicit reminder, ties to 17g)
--------------------------------------------------------------------------------
  Nowhere in this quest's implementation should the literal string
  "Ambrosia" appear as a locked identifier or displayed name until the
  FoodQuality/special-tag naming question (Section 17g) is actually
  resolved. Use a placeholder identifier (e.g.
  totality:bread_perfectly_executed) for the special result until
  final naming lands.

20. IMPLEMENTATION STRATEGY — GUIDE QUESTS AS INTEGRATION TESTS
================================================================================
  FIX: this section previously described batching ALL profession APIs
  first and only THEN adding guide quests — that directly contradicted
  the actual intended cycle and has been corrected to match Section
  2's build order exactly:

    shared foundations -> ONE profession's stable V1 -> THAT
    profession's guide/integration quest (built shortly after, while
    the system is fresh) -> NEXT profession's V1 -> its quest -> ...

  Each guide quest serves DOUBLE DUTY: it's a genuine integration test
  for whatever was just built, AND a player-facing tutorial — neither
  purpose is deferred to "later," both happen close to when the
  underlying system is implemented, not after everything is done.

  First Loaf (Section 19) FOLLOWS Cooking V1 directly and serves as
  ITS immediate gameplay test — this is the first instance of the
  pattern, not a special case. LATER guide quests are expected to
  connect the whole chain across multiple systems at once as more
  professions come online — examples explicitly named for future
  design: water purification, Fishing, fish processing ("River to
  Plate"), cultivation, milling ("Field to Oven"), Husbandry, Carcass
  Processing, and Diet. Each profession's teacher NPC exposes its own
  green guide-dialogue line (Baker->Cooking, Fisher->Fishing,
  Farmer->Cultivation, Rancher->Husbandry, Butcher/Hunter->Carcass
  Processing, Survivalist->Thirst/shelter, Naturalist->Codex/
  Spyglass) — cross-system tutorial quests (like "River to Plate") can
  still be GREEN guide quests even though they span several systems at
  once, since the distinguishing factor is narrative purpose (optional
  guidance) not mechanical complexity (Section 18a/18b's category-vs-
  complexity distinction applies directly here).

  The Codex backend (Section 4) should be built EARLY in the schedule,
  while its FEATURES get taught organically through the various
  profession systems as they come online, plus a small dedicated
  Spyglass introduction (likely folded into whichever guide quest or
  early-game moment makes sense once more content exists) — not as one
  big standalone "Codex tutorial" quest.
