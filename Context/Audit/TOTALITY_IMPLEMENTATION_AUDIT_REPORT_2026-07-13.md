## A. Executive Summary

**Systems inspected:** Economy/Banking/Trading (Credits, Wallet, Banker NPC, shops, trading screen), Smartphone Platform (Phone item/state, equipment slot, app grid, Banking App, Mail/Store), Rest and Fatigue (Rest sessions, bed interception, class-resource recovery, ancestry overrides, multiplayer, outdoor events, Fatigue/Rest Need), and RPG Architecture (ability scores, level/XP, skills, masteries, classes, subclasses, spells, spell slots, abilities framework, species/origins, the shared component/persistence/sync framework).

**Overall level of alignment:** Mixed, and it varies sharply by system. **Rest** is the most mature and most faithful to its design document — session continuation, short-rest limiting, ancestry overrides (Elf Trance), and event-driven recovery ownership all match the document closely, in some respects more elegantly than the document's own "recovered" framing suggests. **Economy** has a solid, safe core (wallet/physical-Credits duality, transactional buy/deposit/withdraw with no dupe paths found) but almost none of the document's shop-economy machinery (account tiers, ATM, ledger, item values, shop runtime state, buyback) exists yet — SELL is a visible but non-functional stub. **Phone** has the right skeleton (one item, dedicated equipment slot, TAB-gating, cosmetic battery) but violates the document's single most emphatic correction by baking the hardware tier into the item's name ("Basic Copper Phone") rather than tracking it as item state, and most of its app grid is locked/decorative. **RPG Architecture** is the most structurally sound of all four (attribute/level numbers match the balance document's own corrected figures exactly; the component/persistence/sync framework is consistent and well-used) but has two significant, currently-open gaps: there is no in-game Skills/Mastery UI at all (a hard-coded stub), and — most importantly — **every spell is currently flagged `isDefault()=true`, meaning every player can cast every registered spell regardless of class**, which is explicitly commented in code as temporary development scaffolding but directly contradicts the Disease/Spell document's locked ownership rule.

**Major conflicts (implementation actively contradicts an adopted design):**
- Every spell bypasses class-eligibility gating entirely (contradicts the Disease/Spell document's Section 2g locked rule) — acknowledged in code comments as a dev-only interim state.
- A "fake" (non-bed) Long Rest advances the **shared world clock** for the entire server, contradicting the Rest document's "Personal Rest completion must NOT force a global time skip" rule — this appears to be a deliberate, reasoned tradeoff (documented in a code comment) rather than an oversight, but it is a real behavioral conflict.
- The Phone item's tier is baked into its name/identity rather than tracked as state, which is the exact mistake the Phone document explicitly warns against by name.
- Trading is opened by bypassing Dialogue entirely (`TotalityNpcEntity.shopId` short-circuits before any dialogue turn), while the Economy document describes the merchant flow as "opening the custom trading screen through Dialogue."

**Major missing implementations (of ADOPTED/RECOVERED-ADOPTED material, not PROPOSED/TBD material):**
- Economy: account tiers, ATM, item-value/50%-sell-pricing, shop runtime state (stock/restock/pool), buyback, Banker security/drops, the Provisioner/first-ordinary-trader NPC.
- Phone: Mail, Phone Store, a shared Economy transaction service for either to plug into, data-driven app/tier definitions, server-side re-validation of locked apps.
- Rest: HP/Hit Dice recovery (entirely absent — no `RestListener` touches health at all), Stamina full-restore-on-Long-Rest, Warlock Pact Magic pool, Wizard Arcane Recovery, Monk Ki (the whole resource, not just its rest hook), Comfort, all five Outdoor Rest Event families (Ambush/Theft/Nightmare/Perception/Visitor).
- RPG: no in-game Skills/Masteries UI, masteries authored for only 3 of 39 skills, no known/prepared spell distinction, dead `startingAbilities`/`grantedAbilities` fields on Class/Subclass/Covenant data that nothing consumes.

**Areas where implementation appears newer/more concrete than the documents:**
- Rest's session engine (real vanilla-sleep integration via two narrow `@Redirect` mixins, grace-window session continuation, dual completion paths for real-bed vs. "fake" rests, priority-sorted `RestEventBus`) is considerably more sophisticated than the document's "RECOVERED, verify against code" framing implies — this is implementation *ahead of* documentation, not behind it.
- The layered `PlayerStats` bonus system (`base + spentPoints + originBonus + classBonus + itemBonus`) and the exact numeric figures (`MAX_LEVEL=150`, `ATTRIBUTE_POINTS_PER_LEVEL=5`, `BASE_SCORE=10`) independently confirm the Balance document's own self-correction is accurate to the running code, which is a positive, low-risk finding.
- Multiclass spell-slot pooling (Full/Half/Third-caster level combination, matching D&D 5e rules) is fully implemented even though there is no player-facing way to actually acquire a second class yet — the backend is ahead of the UI.

**Areas requiring Stefan's design decision:** see Section G. The most consequential: whether the current all-spells-unlocked state is acceptable to leave through further playtesting; whether Warlock is intentionally non-functional for leveled casting right now; whether the global-clock-skip-on-solo-Long-Rest behavior is an accepted tradeoff of Minecraft's single shared clock or needs a different mechanism; and whether `ClassData.startingAbilities` or `ClassFeatureRegistry` is the intended long-term mechanism for granting class-based abilities (both currently coexist, only one is used, by only one class).

**Parts that could not be verified from code alone:** intent behind several dead/unused fields (`ClassData.startingAbilities`, `SpeciesData.RestProfile`, `SkillsMenuScreen`'s apparent absence despite being referenced in project history) could not be distinguished between "abandoned direction" and "not yet wired up" from code alone; see the open-questions list in each per-system section and Section G.

## C. Per-System Analysis

### Economy / Banking / Trading

**What exists:** A working two-form Credits system — `WalletComponent` (account balance, synced `TotalityComponent`, survives death via `RespawnStrategy.ALWAYS_COPY`) and `CreditsItem` (physical item, per-stack amount via data component, capped at 10,000/stack, merges via `InventoryCreditsMergeMixin`, follows ordinary vanilla death-drop rules). `CreditPaymentHelper` centralizes wallet-first-then-physical payment with pre-mutation validation. `BankerNpcEntity` routes exclusively to banking dialogue (`banker_intro.json`/`banker_greeting.json`) with a real account-opening flow (100 physical Credits, or a Persuasion/Intimidation/Investigation skill-check alternative with crit branches) and a deposit/withdraw teller screen (`BankTellerScreen`/`BankTellerHandler`). `TotalityNpcEntity.shopId` opens `TradeSessionManager`/`TradingScreen` directly (BUY functional, quantity-clamped, transactional). Old Copper/Silver/Gold/coin machinery still exists but is explicitly superseded and appears unreferenced by any acquisition path.

**What matches:** The Banker/Merchant ownership boundary (ECON-01), the two-forms-of-Credits split and its death-drop behavior, and the acceptance-check invariants around no-duplication-on-failed-transaction all hold up under direct trace.

**What differs:** Trading opens by bypassing Dialogue rather than through it (ECON-13); physical Credit denominations are a single 5-tier display item rather than named separate items (ECON-03); Credit symbol is `₵` not `Ȼ` (ECON-02).

**What is missing:** Nearly the entire shop-economy layer described in the document beyond the Banker itself — account tiers (ECON-04), ATM (ECON-05), Banker security/drops (ECON-06), a transaction ledger (ECON-07, low urgency, explicitly PROPOSED), item values and 50% sell pricing (ECON-08), shop runtime state/stock/restock/pool (ECON-09/10), Buyback (ECON-11), a functional SELL path (ECON-12), and the Provisioner/"First Sale" content (ECON-14).

**What appears obsolete:** CoinItem family and Denomination/CurrencyHelper (ECON-16); `example_trader.json`'s dead "trade" dialogue choice (ECON-17).

**Relevant code paths:** `api/economy/currency/`, `api/shop/`, `networking/economy/`, `networking/shop/`, `screen/economy/BankTellerScreen.java`, `screen/shop/TradingScreen.java`, `entity/npc/BankerNpcEntity.java`, `entity/npc/TotalityNpcEntity.java`, `item/tools/CreditsItem.java`, `data/totality/shops/`, `data/totality/dialogues/banker_*.json`.

**Recommended next step:** Prioritize `ItemValue`/50%-sell-pricing (ECON-08) first — it unblocks the already-half-built SELL tab (ECON-12) and Buyback (ECON-11). ### Rest

**What exists:** The most mature system audited. `RestManager` (short-rest cap), `RestSessionManager` (the real engine — genuine vanilla-sleep integration via two narrow `@Redirect` mixins, grace-window interrupt/resume, dual completion paths for real-bed-at-night vs. everything else, multiplayer sleep-consensus mirroring), `RestSession`, `RestEventBus` (priority-sorted listener fan-out), `RestDurations`, `AncestryRestOverrides`, `ShortRestActivity`/`ShortRestLength`. Two entry points (Rest ability, bed interaction) share one popup flow. Three generic `RestListener` implementations (charges, abilities, spell slots) currently cover all class-resource recovery — the architecture is genuinely event-driven, not hardcoded per class.

**What matches:** Nearly the entire "recovered, verify against code" section of the document matches exactly, in several cases (grace window = precisely 1 MC hour, Short Rest lengths = precisely 30min/1hr/2hr, Elf Trance = precisely 4 hours) down to the exact tick value. The recovery-ownership architecture (REST-06) is more mature than the document's own framing suggests. Barbarian Rage (REST-22) is a concrete example of that architecture working as intended: its charge pool is registered generically through `PlayerChargesComponent` (`RestType.SHORT`, amount 1), and the shared `onRest()` listener grants exactly +1 charge on Short Rest while unconditionally restoring the pool to max on Long Rest — an exact match to the document's table row, reached without any Rage-specific code in the Rest system itself.

**What differs:** A "fake" (non-bed) Long Rest advances the shared world clock for every player on the server (REST-08) — a real behavioral conflict with the document's multiplayer-fairness goal, though apparently a deliberate, reasoned tradeoff rather than an oversight. The Short Rest cap resets on disconnect rather than persisting (REST-05).

**What is missing:** The recovery table is only ~30% built — HP/Hit Dice (REST-09, the most significant gap, zero code touches health on rest at all), Stamina (REST-10), Warlock Pact Magic (REST-11), Wizard Arcane Recovery (REST-12), Monk Ki (REST-13, the whole resource is absent, not just its rest hook), Comfort (REST-15), Construct Standby (REST-16, blocked on no construct species existing yet), and all five Outdoor Rest Event families (REST-17) are unimplemented. Fatigue/Rest Need (REST-18) is correctly and expectedly absent per its own PARTIAL doc status.

**What appears obsolete:** `SpeciesData.RestProfile` dead enum (REST-16); `PlayerChargesComponent.registerWithRestBus()` no-op (REST-21). The `PlayerRestPoseMixin` deletion cleanup (REST-20) is confirmed clean — no discrepancy, a positive finding.

**Relevant code paths:** `api/rpg/rest/`, `networking/rest/`, `screen/rest/RestChoiceScreen.java`, `client/rest/ClientRestManager.java`, `entity/rest/RestSeatEntity.java`, `mixin/PlayerRestSleepMixin.java`, `mixin/LivingEntityRestSleepMixin.java`, `api/rpg/classes/PlayerChargesComponent.java`, `api/magic/spell/SpellSlotComponent.java`, `init/events/PlayerConnectionEvents.java`, `init/events/RestBedInteraction.java`.

**Recommended next step:** HP/Hit Dice recovery (REST-09) is the highest-priority gap — it's the most fundamental resource in the recovery table and currently has zero implementation, not even a fallback. Warlock Pact Magic (REST-11) should be prioritized if Warlock is meant to be playable in near-term testing, since it currently blocks all leveled spellcasting for that class (cross-references RPG-CLASS-04).

### Fatigue / Rest Need

Entirely and correctly absent (REST-18). The document's own status for this section is `RECOVERED — PARTIAL`, explicitly an unresolved-formula direction, not implementable as-is. No stub, TODO, or partial data model exists anywhere in code, which is the expected state — nothing here should be read as a defect. `ExhaustionManager`/`ExhaustionState` (REST-19) is confirmed to be an unrelated, already-shipped, short-timescale Stamina-based combat mechanic and should not be conflated with the long-term Fatigue/Rest Need concept in future planning.

### RPG Foundations

**What exists:** A layered ability-score model (`PlayerStats`: base 10 + spentPoints + originBonus + classBonus + itemBonus, recalculated centrally), a character level/XP system (cap 150, XP curve `(level+3)*25`), 5 flat attribute points per level, and a component/persistence/sync framework (`api/core/component/`) used consistently across every RPG subsystem audited (stats, skills, masteries, class, spell slots, ancestry, charges).

**What matches:** The numeric ground truth (RPG-ATTR-01) exactly confirms the Balance document's own self-correction; the originBonus layering (RPG-ATTR-02) matches exactly; the component framework's transactional, definitions-vs-mutable-state philosophy independently satisfies the Shared Foundations document's general conventions (CROSS-01) even though it predates that document.

**What differs / is missing:** No character-creation attribute-assignment step exists at all — not Point Buy, not rolling, not any step (RPG-ATTR-03); every player simply starts flat at 10 and earns points only via level-up. This is a stronger gap than "the two proposed generation methods are unbuilt" — there's no generation step of any kind to replace.

**Relevant code paths:** `api/rpg/stats/`, `api/rpg/ancestry/`, `api/core/component/`, `screen/character/tabs/AttributesTab.java` (functional), `screen/character/tabs/OverviewTab.java` (functional).

**Recommended next step:** Resolve whether attribute generation at character creation is still planned (Section G) before investing further in the Balance document's Topic 1 mechanics, since the current flat-10-start model is a complete, working alternative that may simply be the accepted design now.

### Attributes

See "RPG Foundations" above for the shared numeric ground truth. Additionally: `StatAttributeApplier` only centrally applies CON→MAX_HEALTH; STR/DEX modifiers are correctly consumed but done so ad hoc at each combat-related call site rather than centrally cached (RPG-ATTR-05) — a low-urgency architectural inconsistency, not a functional bug. A dead, formula-contradicting pair of methods exists in `RpgDisplayUtils` (RPG-ATTR-04).

### Skills and Masteries

**What exists:** A 39-skill enum across 8 categories, a Skyrim-style XP formula (`skillImproveMult × level^1.95`, confirmed exactly matching project memory), skill level cap 100 (confirmed matching the "150→100" fix noted in project memory), a working mastery-rank system (`MasteryRegistry`/`PlayerMasteries`) gated by skill level and a separate mastery-point pool awarded on character level-up, and concrete XP-award examples for Mining, One-Handed, and Alchemy.

**What is missing:** A player-facing UI. `SkillsTab.java` is a bare "coming soon" placeholder (RPG-SKILL-01) — the only current interaction surface for skills/masteries is `/totality` admin commands. Masteries are authored for only 3 of 39 skills (RPG-SKILL-02). A naming collision exists between the D&D-style `SkillAbilityMap` (check-skill names) and Totality's own `Skill` enum, which happens to share several display names with genuinely unrelated meanings (RPG-SKILL-03).

**Recommended next step:** Build the Skills/Masteries UI (RPG-SKILL-01) — this is the largest player-facing gap found anywhere in the RPG scope, and everything it needs (data, XP tracking, mastery-rank logic) already exists server-side and is fully functional.

### Classes and Subclasses

**What exists:** 4 registered classes (Wizard, Warlock, Barbarian, Monk — many other classes referenced only in comments do not exist as data), a working class-point/class-level system (`getAvailableClassPoints(level) = clamp(level/5, 1, 30)`), subclass selection timing that correctly varies by class (Warlock at initial selection, Wizard at class level 2, Barbarian/Monk at level 3), a `ClassFeatureRegistry` (used only by Barbarian today), and a `ClassLevelUpRegistry` event-fire pattern.

**What matches:** The BG3-style "no subclass at initial selection except where D&D itself requires it" pattern matches project memory precisely.

**What differs/is missing:** Every spell is unlocked for every player regardless of class (RPG-CLASS-01, HIGH severity, explicitly dev scaffolding). Three separate dead fields (`ClassData.startingAbilities`, `SubclassData.startingAbilities`, `CovenantData.grantedAbilities`) coexist with the actually-used `ClassFeatureRegistry`, and nothing but Barbarian uses either mechanism uniformly (RPG-CLASS-03). Multiclassing math is fully built (correct D&D-rules slot pooling) but entirely unreachable through any UI — `SelectClassHandler` hard-blocks selecting a second class.

**Recommended next step:** Resolve RPG-CLASS-03 (which ability-granting mechanism is canonical) before adding more classes, since every new class currently has to choose between two coexisting, non-interoperating patterns.

### Spells and Spell Slots

**What exists:** A working `Spell extends Ability` framework, 14 concrete spells (5 cantrips through level 7), a correctly-implemented D&D-5e multiclass spell-slot pooling table (`SpellSlotTable`), material/component consumption (`ArcaneFocusItem`/`ComponentPouchItem`), concentration tracking with CON-save-on-damage, and a slot-consumption call chain that correctly gates consumption on actual cast success (`markNoEffect()`), not merely on precondition checks.

**What is missing:** Class-eligibility gating (RPG-CLASS-01, the most significant gap in this section), known/prepared spell distinction (RPG-CLASS-02), Warlock Pact Magic as a live pool (RPG-CLASS-04, cross-references REST-11 — Warlock currently cannot cast any leveled spell), spell-scaling-by-skill despite the data existing for it (RPG-CLASS-05), upcasting UI, `SpellbookItem`/`ArcaneScrollItem`/`SpellTomeItem` (all previously flagged as deferred per project memory, now independently reconfirmed absent), and everything above spell level 7 (levels 8–10, including the Level 10 five-axis acquisition model — RPG-CLASS-07, correctly expected to be absent per the doc's own PLANNED status).

**Recommended next step:** RPG-CLASS-01 (class gating) is the most consequential open item in the entire audit from a design-integrity standpoint — it should be resolved (even if the resolution is "leave as-is through this playtesting phase, track for later") before any further content is built assuming class restrictions matter.

### Species and Origins

**What exists:** A fully working 3-screen selection flow (Species → Origin → Confirm), ~29 origins across ~10 species, `OriginData.startingAbilities` genuinely wired end-to-end (the one ability-granting mechanism in the whole RPG scope that fully works as designed), and the `AncestryRestOverrides`/`RestProfile` touchpoint into the Rest system.

**What matches:** Fully matches project history/memory description; no discrepancies found against any of the audited documents (species/origins are not directly covered by the in-scope documents beyond the Rest document's ancestry-override section, which matches exactly for Elf Trance).

**Recommended next step:** None urgent — this is one of the most complete and lowest-risk systems audited.

### Cross-system foundations

**What exists:** Totality's own component/persistence/sync framework (`api/core/component/`) is the de facto implementation of the "definitions are immutable, player progress is mutable component state, multi-step operations are transactional" philosophy that the Shared Cross-System Foundations document states as a general cross-cutting convention (CROSS-01) — even though the framework predates that specific document and uses different names. Every RPG/Economy/Phone component audited follows an identical registration → attach → sync (one shared `totality:component_sync` packet type, keyed by `Identifier`) → NBT persistence → respawn-copy-strategy pattern.

**What is missing:** The entire Food Ecosystem design corpus (Codex/Discovery, Environment, Product Condition, Fluid Material, Processing, Ingredient APIs) and the Disease API have **zero code footprint** (CROSS-02) — confirmed by repo-wide search finding no matching classes at all. This is fully expected (these are forward-looking documents for systems not yet begun per their own stated build order) and should not be read as a gap in current work, but it is worth stating plainly since these documents constitute half the material this audit was asked to read. The one piece of shared vocabulary from that corpus that *is* directly relevant to in-scope systems — the `UnlockRequirement` AllOf/AnyOf/Condition tree — is also entirely unbuilt (RPG-CLASS-08), consistent with its own PROPOSED status.

**Recommended next step:** None required now; when Food Ecosystem/Chemistry/Disease work actually begins, the existing `TotalityComponent` framework is a solid, proven foundation to build on rather than reinventing persistence/sync per new system.

## G. Questions for Stefan

1. **Spell class-gating:** Every spell is currently flagged `isDefault()=true` (unlocked for every player regardless of class), with a code comment stating this is temporary "during development."
